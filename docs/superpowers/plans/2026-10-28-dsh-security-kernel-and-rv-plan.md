# RVguarder 安全内核改造与研究验证计划

**执行者：DeepSeek V4；复核者：Codex。**

**总体目标：** 先解决 DSH 中因语义适配、策略粒度和重复审批造成的正常任务阻塞，再围绕明确的威胁模型增强运行时防护，最终形成可复现、可比较、可用于论文论证的工程与实验基础。

**实施顺序：**

审批归因 → DSH 事件与效果建模 → PMKB 与任务授权改造 → 执行闭环及前端验收 → 威胁覆盖分析 → 参数化 RV 增强 → 论文实验。

本计划基于当前静态分析。**“几乎每步审批”的实际原因占比尚未测量；已有历史实验不能直接证明当前 DSH 部署的防护效果。**

## 一、执行约束与开始前检查

### 1.1 不得破坏的约束

- 直接在 `master` 分阶段提交，保留用户已有改动，不进行无关重构。
- 优先保证 DSH 0.2.1-rc.2 / rc.3；共享内核修改同时验证 OpenClaw。
- DSH 默认 fail-closed 与 OpenClaw 故障透传分别保持原有约定。
- PMKB 负责单步授权，RV 只能提高风险裁决；降低误审批应修正上游证据、规则或授权，不能让 RV 覆盖 PMKB 的审批、阻断。
- 未知工具、缺失可信身份、未知效果不能因“降低审批率”自动放行。
- LLM 只提供语义建议，不签发授权，不证明执行成功，不把不可信参数提升为可信证据。
- 保留语义子代理的工具隔离，验证它不会递归触发 Guard 或获得实际工具执行能力。
- 使用临时 profile、合成数据和隔离接收端测试；不得读取或输出真实密钥，不修改日常 profile 来掩盖测试问题。
- 普通审批一次通过，不自动变成永久授权；`danger-full-access` 不等于用户授权所有业务行为。

### 1.2 DeepSeek V4 必须先检查的内容

| 检查对象 | 必须回答的问题 |
|---|---|
| `AGENTS.md`、[项目开发记忆](../../dev/project-memory.md)、DSH 阶段及修复记录 | 哪些能力已实现、哪些只是规划、哪些验证只适用于旧版本？ |
| Git 状态、最近提交、实际加载插件与后端路径 | 运行的是当前源码构建产物，还是旧安装包？ |
| DSH 插件入口、宿主 SDK、审批及 dispatch 管线 | 谁触发审批？批准后是否重评估？是否重复 dispatch？ |
| DSH adapter、tool hook bridge、ToolCallIR、Trace 编译 | 原始参数是否正确映射？哪些信息被丢失或错误推断？ |
| PMKB evaluator、permission diff、risk graph、策略 JSON | 每一种 ask 来自哪个分支？是否存在规则冲突、覆盖不足或错误 scope？ |
| RV DSL、权限监视器、成功证据与状态存储 | 哪些状态消费 proposed，哪些消费 succeeded？是否跨任务串扰？ |
| 宿主授权、受控字节收据、委派身份 | 哪些已有机制可复用？哪些 DSH 路径尚未接通？ |
| 前端 API、审批展示、SSE、HostPanel | 能否区分宿主审批、Guard 审批、阻断、故障和未知状态？ |
| Python、Node、前端、E2E 测试环境 | 哪些失败是产品问题，哪些是依赖或环境问题？ |

特别复核三个判断，不能凭上一轮结论直接修改：

1. 工作区写入和一般进程执行默认审批，可能是现有策略的明确设计。
2. `run_code → code_execution` 可能将 PTC 容器与内部效果混在一起；必须用实际调用链证明重复审批。
3. 缺少 `current_permissions` **不等于必然审批**；必须追踪最终生效的 coverage、excessive permission、rule effect 等条件。

**阶段产物：** 当前架构图、版本清单、测试基线、待验证假设表。每项结论标记为“代码确认／实测确认／尚未验证”。

## 二、第一阶段：建立审批归因，确定真正的问题

**本阶段先加观测和复现，不修改放行策略。**

### 2.1 建立逐调用决策记录

复用现有审计及调用标识，补齐：

- host、instance、principal、agent、task、session、call、parent/root call。
- 原始工具身份、适配版本、规范操作、资源与目的地。
- 证据来源、可信等级、缺失字段、效果覆盖情况。
- PMKB 候选及命中规则、权限差分、RV 命中与各层裁决。
- 最终动作及稳定的原因码。
- 审批发起方、审批请求 ID、批准或拒绝、dispatch 和完成状态。
- 策略版本、运行版本、耗时。

记录解释和摘要，不默认保存原始敏感内容。缺失 task 等字段应保留为未知，不能为了完整性自行伪造。

原因至少区分：

`policy_requires_approval`、`unknown_tool`、`missing_evidence`、`scope_unknown`、`permission_excess`、`grant_invalid`、`rv_escalation`、`host_approval`、`backend_failure`。

去重指标区分“重复记录同一张审批卡”与“真的创建了多张审批卡”。

### 2.2 建立冻结的正常任务集

覆盖工作区读取、搜索、多文件编辑、新建文件、测试、构建、公开网页访问，以及带明确授权的受控发送。

分别通过 native 工具、shell、PTC、已适配 MCP 执行等价任务；区分首次调用、重复调用、并发和子代理。

测试/构建可能执行任意项目代码，**不能预先标记为天然安全**；应记录其授权和隔离条件。

输出：

- 每任务审批次数、每调用审批比例。
- Guard 与 DSH 各自贡献。
- 各原因占比、任务成功率、阻断率、耗时。
- 外层 PTC 与内层工具的实际调用关系。
- 每个主要问题对应一个最小复现。

**验收门槛：** 测试集内每一次审批均能归因；“未知原因”计数为零。尚无法观测的宿主审批必须明确列为观测缺口，不能混算。

## 三、第二阶段：改造 DSH 事件与效果建模

### 3.1 保留工具入口，分离操作、效果和授权

不推翻已有 ToolCallIR 与 Authorization Trace，先扩展并消除重复推断。

统一表达：

| 层次 | 内容 |
|---|---|
| 调用身份 | 注册工具身份、调用树、主体、任务、执行环境 |
| 规范操作 | read、write、execute、send、grant 等已有 canonical operation |
| 预期效果 | 可能访问的资源、目的地、能力范围及未知部分 |
| 实际效果证据 | 执行成功、实际消费字节、输出版本、收据 |
| 授权证据 | 授权主体、范围、有效期、用途、委派与撤销状态 |

**预期效果不能写成已发生效果。** shell 中出现多个命令，也不能因此虚构多个已成功执行事件。

可信度按来源保存：宿主认证字段、登记执行器证据、静态推断、LLM 建议、不可信参数分别处理。

### 3.2 按执行路径适配

- **原生文件工具：** 核对参数契约、可信 cwd、实际执行路径与命名空间；覆盖 Windows 大小写、UNC、junction/symlink 等边界。
- **shell：** 复用并收紧现有命令分析。只有已支持语法且效果完整可判定时才能给出确定结论；管道、重定向、动态求值或脚本副作用不可因命令名前缀而放行。
- **PTC：** 区分运行容器和内部工具调用，实测直接文件/网络/进程访问是否可能绕过 Hook。
- **MCP：** 按服务器、工具注册身份及明确参数契约映射，不按工具名相似度继承安全契约。
- **子代理：** 使用可信 parent/root 身份，分离状态；委派权限只能缩小父级授权，不能自动继承全部历史许可。

### 3.3 PTC 去除重复审批的硬条件

只有同时证明以下条件，才能将外层 `run_code` 视为纯调度容器：

1. 内部有副作用的工具调用全部经过有效门禁。
2. 容器直接 I/O 被隔离或纳入同等门禁。
3. 调用身份、取消、重试与完成事件能够可靠关联。

条件不满足时保留外层风险决策，并在前端解释覆盖缺口。不得为了正常任务流畅而简单跳过 `run_code`。

**验收门槛：** 同等效果在已支持入口产生一致的规范语义；不能完整识别的路径明确标记 partial/unknown，不能误标完整覆盖。

## 四、第三阶段：改造 PMKB 与任务授权，减少不必要审批

### 4.1 策略分为三类

| 类别 | 默认处置 |
|---|---|
| 证据充分、规则明确允许的低风险行为 | 自动允许并审计 |
| 可由明确任务授权覆盖的行为 | 授权内自动执行，越界重新决策 |
| 已知高风险禁止行为或证据不足行为 | 按规则阻断或请求审批 |

不把所有写入改为自动允许，也不把所有进程执行改成只读命令白名单。

正常开发任务通过**明确的任务范围授权**减少重复审批：例如授权指定工作区内的普通文件读取、创建和修改；默认排除凭据、授权库、Guard 状态、宿主配置、持久化入口和外发能力。排除项优先于一般范围授权。

任意 shell、构建脚本、删除及网络能力不因具有“开发任务”标签自动获得权限。

### 4.2 复用现有宿主授权机制

先核对已有实现，再扩展到 DSH。区分：

- 精确单次许可：绑定当前调用及必要资源版本、目的地。
- 有界任务许可：绑定可信 task、主体、工作区、操作集合和时效。
- 显式委派许可：限定子代理可继承的子集。

任务授权由可信宿主管理入口签发；Agent 参数、文档内容及模型解释不能签发。宿主无法提供可信 task ID 时，不启用跨调用任务授权。

默认任务许可在任务结束或撤销时失效，并设置有限过期时间；重启后先重建可信任务关系，不能仅凭旧 session 名称恢复。

前端可展示范围与剩余有效期，但不得把普通浏览器接口变成任意签发授权的入口。

### 4.3 修正规则与去重逻辑

- 修复错误的路径 scope、遗漏字段、错误 operation mapping。
- 分离“策略主动要求审批”和“由于证据缺失降级审批”。
- 审批复用必须验证主体、任务、操作、参数摘要、资源及目的地仍符合授权。
- 参数变化、资源替换、授权撤销或策略变化后重新检查。
- 同一审批请求重试采用幂等处理；不能仅凭工具名、时间接近或会话相同去重。
- 保留硬阻断优先级和 RV 单调合并约束。

**验收门槛：**

- 已明确允许的只读任务，Guard 新增审批为零。
- 用户明确授予范围的普通工作区编辑任务，授权范围内不再逐文件审批。
- 同一调用不得产生重复 Guard 审批或重复执行。
- 越界、过期、篡改、撤销和跨主体复用全部进入预期拒绝或重新审批路径。
- 同时报告 DSH 自身审批，不能把无法消除的宿主审批算作 Guard 已解决。

## 五、第四阶段：执行闭环与现有前端联调

### 5.1 执行闭环

明确区分 proposed、approved、dispatched、succeeded、failed、cancelled 和 outcome_unknown。

- 前置检查不写入成功历史。
- 只有可信完成证据可扩充成功状态。
- 重复回调幂等处理；乱序事件不能制造不存在的因果关系。
- 超时不等于未执行，取消也不证明副作用已回滚。
- 后端恢复不得自动重放不确定调用。
- 执行前重验证授权及关键资源版本；能使用固定内容快照的执行器应消费同一快照。
- 对无法消除的检查与执行竞态，明确降低保证，不用“再次 hash”宣称完全解决 TOCTOU。

### 5.2 前端对接

沿用现有页面、状态管理和 SSE：

- 显示“谁要求审批、命中何规则、缺什么证据、授权是否有效”。
- 将外层 PTC 与内层调用折叠展示，同时保留独立裁决。
- 分开展示执行失败、策略拒绝、后端不可用和未知结果。
- 展示任务授权范围及状态；审批仍走受信任的宿主流程。
- 新增审批统计与主要原因，不展示密钥或原始敏感内容。
- 后端字段采用兼容性扩展；旧记录显示“未记录”，不能默认为安全。

**阶段交付：** 单元测试、真实 SDK 联调、DSH 浏览器 E2E、OpenClaw 回归，以及安装包与实际加载产物一致性证据。

**第一复核点：** 完成至此后交 Codex 复核。审批问题的修复应作为独立可验收版本，不等待研究型 RV 改造完成。

## 六、第五阶段：基于官方文档建立威胁与能力矩阵

执行时将官方资料固定到 commit SHA，记录访问日期，并与已安装 rc.2/rc.3 SDK 对照。当前 master 文档不能直接作为旧 SDK 的实现合同。

必读：

- [DSH 官方安全说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/SAFETY.md)：模型生成代码、恶意输入、不可信插件及可访问资源的风险，审批和沙箱不能提供绝对隔离。
- [DSH 沙箱文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md)：文件效果边界、partial enforcement、完全访问模式，以及网络与进程可见性不在该模式词汇覆盖范围内。
- [DSH 工具管线文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/tools/README.md)：执行与展示结果的区别、作用域限制及自定义执行器的管线覆盖问题。

逐项填写：

**威胁 → 攻击入口 → 可观测证据 → 执行前阻断点 → 当前能力 → 缺口 → 测试 → 保证边界。**

至少覆盖：

1. 单步越权读写、删除、进程执行。
2. 提示注入诱导的跨步骤操作。
3. 敏感数据读取、变换、编码及外发。
4. 授权后资源或目的地替换、授权重放。
5. 跨会话及跨子代理权限混淆。
6. PTC/MCP/自定义执行器绕过。
7. 恶意插件直接访问 Node、系统或网络。
8. 审计、状态、授权库及 Guard 控制面的篡改。
9. 并发、长间隔、重启及资源耗尽规避。

能力必须归为：**已实测防护／已实现待验证／只能请求审批／需宿主或 OS 配合／当前不覆盖。**

不能把 `ask` 计为独立阻断，也不能把渲染层脱敏当作原始数据访问控制。

## 七、第六阶段：增强现有 RV，按证据决定是否更换引擎

### 7.1 技术选择

**默认保留现有自动机与 DSL，增强参数化、时间、证据与执行语义。**

自动机本身就是形式化方法的一种。应解决的是当前性质能否准确表达、事件是否可信、执行是否受控，而不是仅替换“更高级”的名称。

首批增强：

- 按主体、任务、资源版本、目的地参数化监视器。
- 区分调用顺序与真实因果关系，支持并发调用。
- 明确有限轨迹语义：已违反、当前前缀未违反、证据不足；不得把“暂未发现违规”称为未来安全。
- 时间条件使用可验证时钟与明确过期语义。
- 窗口淘汰、状态容量不足或重启丢失不能静默变成安全。
- 输出可重放的违反见证及最小必要证据。

### 7.2 首批性质

| 性质 | 必要证据与执行动作 |
|---|---|
| 外发须有匹配授权 | 发送前验证主体、任务、实际内容版本、目的地及有效期 |
| 派生敏感数据保持约束 | 受控变换生成可信血缘；外发前验证解密级或发送许可 |
| 委派不得扩大授权 | 子代理能力必须是明确委派范围的子集 |
| 成功证据不可伪造 | proposed、失败、重复和不可信完成事件不能生成成功事实 |
| 授权不可重放或跨任务挪用 | 单次许可原子消耗；任务许可校验生命周期与身份 |

血缘只能覆盖提供可信收据的执行器；不能因为发生过“读取后发送”就断言发送内容必然来源于该读取。

### 7.3 更换引擎的条件

先实现性质参考解释器和固定轨迹集，再评估现有 DSL：

- 能表达且满足正确性、状态和延迟预算：继续扩展。
- 必要性质无法表达：隔离出最小缺失语义，进行独立后端原型。
- 外部监视器在同一轨迹集通过语义等价及性能比较后，才考虑替换。

首个改造版本不引入新的重量级引擎依赖。候选后端评估必须记录许可证、维护状态、集成成本、解释能力和结果差异。

**第二复核点：** 威胁模型、性质语义、参考解释器和第一批监视器完成后，由 Codex 检查是否存在过度承诺、错误状态更新或授权漏洞。

### 8.2 实验设计

比较五组：

1. DSH 原生控制。
2. 当前 RVguarder。
3. DSH 语义适配后。
4. 加入任务授权后。
5. 加入增强 RV 后。

另做授权、血缘、时序监视、委派约束的消融。模型、提示、任务、宿主版本、基础权限及审批响应方式保持可比。

审批策略分别报告“自动拒绝／自动批准／固定人工协议”，避免把人类兜底效果误归因于插件。

指标包括：

- 攻击实际副作用发生率。
- 正常任务完成率、误阻断率。
- 每任务审批次数，按 Guard 与宿主拆分。
- 决策延迟 p50/p95/p99、内存及状态规模。
- 证据完整率与规则解释可追溯率。

攻击后果由隔离文件状态、进程记录和接收端字节收据独立判断，不仅依据 Guard 日志。

按任务族、攻击机制和入口划分开发集与留出集；规则冻结后才运行最终评估。结果保留失败、跳过、重复运行、随机种子和置信区间。

另进行相关工作检索，重点比较 Agent 授权、提示注入防护、信息流和 RV；没有文献对比前，不宣称方法具有新颖性。

### 8.4 Codex 后续复核标准

我会重点检查：

1. 审批减少是否来自正确授权和更准确建模，而非放宽未知行为。
2. PTC、MCP、子代理是否存在绕过路径。
3. 授权是否能被伪造、扩权、重放或跨任务复用。
4. 并发、超时、重启与重复回调是否破坏执行或状态一致性。
5. 前端解释是否与最终裁决一致。
6. 实验是否测量真实后果，是否存在数据泄漏或选择性报告。
7. 论文结论是否严格受实际覆盖和实验证据支持。
